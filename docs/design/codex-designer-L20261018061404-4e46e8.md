## (C) 推薦組合

以下是建議實作契約，**尚未實作或驗收**。

**1. 題庫分成完整目錄與新題候選，不再物理刪除題目。**

```text
catalog.allCards   完整題目、原始 ID、觀念及來源
catalog.activeIds  可以排成新卡的 ID
catalog.merged     被併題 → keep[]、why；代表出題／來源關係
catalog.version   本次題庫版本
```

四站只負責提供資料：

- 數學：`ALL_GENERATED` 為完整目錄，`CARDS` 為新題候選；輸出 family 分組及候選關係。
- 社會／國語：`ALL_CARDS` 為完整目錄，`MERGED` 決定新題候選。
- 自然：未過濾的 `BASE_CARDS＋bank_extra` 為完整目錄，`G5_MERGED` 決定新題候選。
- 匯入題沿用現有內建題優先規則，不能因新增 archive 而讓原本被遮蔽的同 ID 匯入題復活。

[已驗證] 本站目前產生 **184 題、64 個 family、新題候選 105 題**。這證明目前分組結果，不代表所有分組的教學等價性都已驗證。

**2. 原始作答與已排任務保留原 ID。**

| 資料 | 題庫裁減時的規則 |
|---|---|
| `cards`、`log` | 不改 ID、不搬成績、不複製有效日。 |
| 已存在的 `days.planIds／doneIds／touched` | 不因 active 清單改變而刪除或替換。 |
| 當日 `session.queue／answered／wrong／kinds` | 保留；從完整目錄取回原題，繼續作答。 |
| 尚未完成的補救題／實驗引用 | 同樣能查回原題，避免只修主佇列。 |
| 新一天的新卡 | 僅從 `activeIds` 選取。 |
| 已練舊卡的到期複習 | 依原 `cards[id]` 排程，到畢業為止。 |

`cardById()` 查完整目錄；「是否要排題」由另外的 selector 決定。**不能再讓一個 `allCards()` 同時承擔查題、排題與統計。**

真的缺少題目內容時，列為可見的資料缺口，保留引用；不能默默刪除任務或自動宣布完成。

**3. 地圖、觀念階段及複習入口使用 core 同一份投影。**

每個觀念的統計母體：

```text
目前新題候選
∪ 已實際練過的舊題
∪ 當日計畫／進行中回合仍引用的舊題
```

按實體 ID 去重：

- 做過題數只看原題作答證據。
- 階段使用同一母體及原本出口題／畢業條件。
- 單純裁題不得使已練題數下降，也不得讓發芽回到種子。
- 「直接闖關」「全部複習」「再練答錯的」的題數、按鈕與出題清單，由 core 一起提供。
- 數學 `g2max、g2up` 的例子，結果保留 **2／11、發芽了**；不把它們冒記成 `g0max、g1max`。

這個方案的明確代價是：保留題與已練舊題可能暫時一起複習。若要求立即壓低這部分負擔，應另做有明確等價規則的承接設計。

**4. 「沒有任務」「已完成」「可補做」分開。**

core 明確輸出：

- `planStatus = empty | open | complete`
- `canMakeup` 及不能補做的原因

空計畫不是完成；但沒有今日待做任務，也不應一律被 `MAKEUP_TODAY_FIRST` 擋住。有可用補做題就可開始，沒有則說明沒有可用題。未實際作答，不寫 `touched`，不增加連續練習天數。

對於**已被舊版寫成空陣列**的計畫，不猜原本有哪些卡；保留現存證據，以獨立的補做資格解除死鎖。

**5. 補做只由明確操作結算。**

移除 `pruneVanished` 的結算副作用。core 提供「可繼續」「可結算」「已結算」「已跨日」狀態，畫面只呈現。

結算請求綁定：

```text
目標補做日＋實際作答日＋本次要求結算的題目 ID
```

以實際作答日的 `touched`、當日計畫及已結算紀錄核對，避免依賴會截斷的 `log`；同一張卡在同一實際作答日只能供一個補做日使用。**不從後來被別的分頁換掉的 `session.makeup` 推定歸屬。**

一般答完、停輪、重新載入後待結算，都走同一條操作；寫入成功後才顯示補做完成。跨午夜仍採現有語意：昨天未結算的卡不冒算成今天作答，目標日保持可補。

**6. 安親班是來源標籤，不是掌握度 alias。**

由完整目錄的來源與合併關係，在共用 core 推導 `ANQIN_ALSO` 等價結果：

- 被併安親班題的保留代表仍能進安親班複習卷。
- 多條關係指向同一保留題，只列一次。
- 保留原生安親班來源與繼承來源的區別。
- 刪掉合併表一行後重新推導，不能留下永久污染的安親班標籤。

若被併題已練過，依本方案可同時保留該舊題與保留代表；畫面須如實計算兩個實體題目。

**7. 四站共用核心，app 只做一次同型接線。**

將存檔 key、診斷期放進站別設定；題庫差異放進資料 adapter。`core.js` 共用完全相同的實作，統一輸出：

```text
progressByConcept、stages、reviewSets、redoIds、
planStatus、canMakeup、makeupStatus
```

四個 app 移除自行計算的地圖進度、`reviewStats()`、`redoIds()` 與合併傳遞規則，改讀這些結果。可以共用接線 helper，避免日後四份各修一次。

**8. 明定多分頁與撤回界線。**

- 同版分頁的寫入應在共用 store 排他流程內完成「重讀→reduce→驗證→寫入」；目前的 `refresh()` 只處理循序更新，不能宣稱具有原子互斥。
- 若支援新版與既有舊頁混開，需有版本拒寫機制，例如新 schema `v4`；[現有 decoder](/Users/william/Documents/g5-math-review/src/core.js:537) 會拒絕非 `v3`。**只增加幾個舊版不認識的欄位不夠，舊頁仍可能執行 prune。**
- 已進入讀寫臨界區的舊版操作仍是切版風險，不能用版本號假裝完全解決。外部同步端是否接受新版存檔：範圍外、未讀。
- 刪除合併表一行，只改新題候選與來源投影；不撤銷歷史、不重開已完成計畫。恢復的未練題自下一份新計畫納入。若因此增加目前觀念要求，應顯示新增待練題，而非把舊紀錄歸零。
