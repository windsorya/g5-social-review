## (C) 推薦組合

**採①＋③＋④。沿用原設計 S0–S2 的資料權威與封存方向，以下規則補強 S3；F1/F2、X1–X4 不放寬。**

**C1．核心結果與單一狀態**

核心公開操作統一回傳下列資訊；欄位名稱可依既有命名調整，但語意不可省略：

```text
ok、error、storageStatus、phase
pendingId、acceptedIds、state／snapshot
writeOutcome：notAttempted／unconfirmed／confirmed
自然站另含：appliedChoice、archive、choiceLocked
```

`storageStatus` 是唯一的 READ／SAVE／失效畫面狀態。`pendingAction` 是待辦資料，`archive` 是封存工作進度，不能再各自推導另一套 READ／SAVE 提示。

| 狀態 | 核心判定 | 畫面契約 |
|---|---|---|
| `ok` | 本操作必要讀取完成，必要寫入已確認；沒有阻擋本流程的未完成操作 | 才可能公布；仍須檢查本次操作 ID、學習流程及業務前提 |
| `saveFailed` | 寫入／刪除未完成，或仍有待補存操作 | 保留畫面與待辦，顯示重試入口，不公布完成 |
| `readFailed` | 任一必要讀取或回讀拋錯；結果不能確認 | 保留畫面、句數、runId、待辦；允許重新檢查，不推進學習畫面 |
| `stale` | 已確認現行資料與本頁依據不同 | 沿用整頁失效流程；同一 store 不得自行回到 `ok` |

補充轉移規則：

- READ 優先呈現為 `readFailed`，但保留原 pending，不將它遺失或換成新操作。
- 讀取恢復後，若待存尚未完成，狀態回到 `saveFailed`；只有補存及後續必要步驟都成功，才回 `ok`。
- `check()` 讀成功只證明本次檢查成功，不能清掉未補存操作或未完成 tick。
- `stale` 只能經既有確認／重載流程建立新 store 後解除。
- `SCHEMA`、`LEGACY`、`BAD_ACTION`、`CONFLICT` 等保留業務錯誤，不硬塞成寫入失敗，也不能因儲存可讀就視為操作成功。

移除可獨立修改的 `readNote`。`saveFail` 若保留為 DOM id，只能由統一 renderer 產生。`banners()` 改為純渲染，不更新旗標；各入口不再呼叫 `readOk()` 或手動移除錯誤 DOM。

READ 文案改為「暫時讀不到紀錄，先停在這裡，請再試一次」。V 已寫但尚未回讀確認時，顯示「寫入結果尚未確認，請重新檢查」。**不得一律宣稱「沒有存」**，因為前一步可能已存入。

**C2．核心錯誤分類不得被中途改寫**

- `refresh()`、`flushPending()` 使用結構化結果，區分 READ、WRITE、STATE_CHANGED；不再共用 `"fail"`。
- `dispatch()` 遇必要讀取失敗，一律回 `ok:false, error:"READ", storageStatus:"readFailed"`。
- 有另一筆 pending 時，保留該筆 `pendingId`；讀取失敗仍回 READ，不能包成 `SAVE_PENDING`／`SAVE_FAILED`。
- 真正寫入失敗才回 `SAVE_FAILED`。`SAVE_PENDING` 若保留，僅表示舊操作的寫入尚未完成，不得掩蓋 READ。
- `retry()` 直接保留下游錯誤種類；有／無 pending 都遵守同一契約。
- `dup`、`accepted(id)` 不構成繞過本輪 READ 或失效檢查的理由。

**C3．共同 `resume()` 與畫面公布點**

切回分頁及「再存一次」共同呼叫：

```text
resume(reason)
  → check 當下資料
  → retry 既有 pending（如有）
  → dispatch(tick)，完成跨日／維護狀態
  → 取得本輪已核對的結果快照
  → 統一更新提示及公布畫面
```

每一步都檢查 `ok`；任何失敗立即停止後續流程。中途只能更新錯誤提示，不得先公布答案、增加句數、切頁或清除 `lab`。

補存成功後若 tick 再 READ，**已存內容保留，畫面仍停住**；下一次 resume 以相同操作 ID 確認，不重複記錄。這是畫面延後公布，不是回滾儲存。

畫面公布須同時符合：

1. 本輪必要核心操作全部成功。
2. 最終狀態為 `ok`，沒有阻擋本流程的 pending。
3. 要公布的操作 ID／runId 與本輪結果相符。
4. 使用本輪快照；不得用先前的 `accepted()` 結果替代。

| 入口 | 核心呼叫及畫面更新 |
|---|---|
| 作答 | 保留同一操作 ID 呼叫 `dispatch(answer)`；成功才標示答案回饋與下一題。READ 或待存時保留輸入及目前題目 |
| 下一句／下一步 | 未完成的步驟呼叫 `dispatch(labTask)`；已補存的步驟呼叫 `check()`。只有核對成功且步驟確實已存，才增加可見句數 |
| 切回分頁 | visible 時呼叫 `resume("visible")`；失敗保留 screen、lab、runId、句數。成功後才依既有跨日規則更新画面 |
| 再存一次 | 上方與題目內按鈕皆呼叫 `resume("retry")`；按鈕位置不改變流程。不得只因舊答案已接受就公布 |
| `labRefresh` | resume 內僅使用本輪已驗證快照重繪，不再偷偷讀取或呼叫另一條恢復鏈；獨立呼叫時先 `check()`，失敗不得落到 `route()` |
| `tick` | 一律經 `dispatch(tick)`；READ 回 READ。失敗不得觸發跨日切頁；無 action ID 也須保留「維護尚未完成」，由後續 resume 重做 |
| storage／同步通知 | 經核心 `check()`／既有 `invalidate()` 取得結果，再交統一接收器處理；不得直接清提示或重畫舊資料 |

同一輪只能有一個恢復流程。延遲 callback 須核對畫面世代；旧結果不得在新畫面上公布。

**C4．自然站家長選擇：每次按鈕重驗 V/O/A**

沿用 `V=g5sci.v3`、`O=g5sci.v1`、`A=g5sci.v1.archived`。

1. **每個家長流程按鈕都重查。** 選「恢復」、選「從頭開始」、確認、取消／返回選項、重新檢查、重試封存，均先重讀 V/O/A；必要讀取失敗即停止。不能因按鈕先前已顯示就沿用開頁判斷。
2. **衝突以當下內容計算。** `O !== null && A !== null && A !== O` 即為衝突；「恢復」與「從頭開始」都不得建立 V、覆蓋 A 或刪 O。移除「有衝突仍可從頭開始」的提示，符合原 T24。
3. **寫入前再次確認前提。** V 仍不存在、來源原文未變、目前無封存衝突，才能建立候選 V。已有合法 V 就以 V 為主；外部替換則失效，壞 V 走壞檔流程。
4. **首次選擇綁定候選內容。** 記憶體保留 `attemptId／chosenMode／sourceRaw／candidateRaw`。V 寫後回讀失敗，回 READ 並標示 `writeOutcome:"unconfirmed"`；不刪 V、不刪 O。
5. **未確認時禁止改選。** UI 僅保留「重新檢查」；即使程式直接呼叫相反選項，核心也拒絕切換，不接受第二次 choice 作為成功文案依據。
6. **重查後依實際 V 決定。** V 等於首次候選且驗證通過，承認首次選擇；V 確認不存在，才解除未確認狀態並允許重新選擇；V 不同或不合法，停止並轉失效／壞檔處理。
7. **成功文案使用 `appliedChoice`。** 由核心核對首次候選與實際 V 後回傳，UI 不使用最近一次按鈕參數。重開頁面若已失去首次選擇證據，只能說「已載入目前紀錄」，不能猜恢復或從頭開始。
8. **封存每一步向前核對。** 寫 A 前確認目前 V、O、A；刪 O 前確認 A 原文一致且 O 未換；刪後確認 O 不存在。任何 READ 停止本次流程，已有 V 不回滾。

V 已確認、封存未完成時，保留「進度已存，舊版封存未完成」的部分完成資訊，不能宣布完整封存成功；封存問題也不得使合法 V 被空白或舊資料覆蓋。

**C5．封存 pending 必須能由現況解除**
